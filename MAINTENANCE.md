# Maintenance and review plan

Review technical references quarterly and when a relevant security advisory, major framework release, API deprecation or search-policy change appears. This is a recommended cadence; a completed review must be recorded rather than implied by an unchanged date.

For each review, record the source URL, retrieval date, version context and affected document. Compare stable capabilities with experimental features and roadmap statements. Update the recommendation and its acceptance checks together. Never turn a future release into an implemented service claim.

Check public links, local navigation, example headers and portfolio descriptions. If a source is unavailable, label the uncertainty and find an authoritative replacement. Keep an existing case study's scope accurate instead of adding unverified results. Recheck AI tool permissions, data retention, budgets and provider controls before recommending a new workflow.

Record meaningful changes in CHANGELOG.md. A release note should explain the practical difference for a reader, not manufacture activity. Before using guidance in a client project, check installed versions, dependencies and the actual operating environment. Sensitive system changes still require the project owner's approval.
